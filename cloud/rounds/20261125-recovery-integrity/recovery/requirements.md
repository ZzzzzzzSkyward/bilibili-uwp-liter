## 2. Recommendation state, request and publication contract

Keep the public default construction, RefreshCommand/LoadMoreCommand and GetRecommend entry usable by RecommendPage. Add awaitable internal cores/test seams as needed; async-void remains only at command/event adapters and catches/logs all propagated exceptions. One request owns the VM at a time, including the initial navigation call; duplicate refresh/append/retry activation while pending schedules no second request and cannot change cursor or error ownership.

Use explicit VM state/properties, with names chosen consistently during implementation. Required externally observable states are:

| State | Rows/banner | Visible region/action | Automatic append |
| --- | --- | --- | --- |
| Initial loading | No committed rows | Progress, no empty/error text | Off |
| Successful empty (including all-filtered initial batch) | Successful empty collection; optional valid banner may remain | `暂无推荐内容` and refresh | Off |
| Initial required failure | No rows published | Persistent `推荐加载失败` and retry initial request (`idx=0`) | Off |
| Ready | Committed rows/banner | Existing cards/layout and manual load more | On when a usable continuation exists |
| Refresh pending with rows | Existing exact collection/banner retained | Progress; cards remain usable | Off |
| Refresh failure with rows | Exact previous rows/order/banner/cursor retained | Persistent refresh failure and retry refresh | Off until an explicit successful attempt |
| Append pending | Existing rows/order retained | Footer progress | Off |
| Append failure | Exact previous collection/order/banner/cursor retained | Footer `加载更多失败` and explicit retry of the failed idx | Off until explicit retry |
| Successful append without progress | Existing rows retained | Non-error `暂时没有更多推荐` with manual load more | Off; no claim that the feed is permanently exhausted |

Successful nonempty append adds its staged rows once, then advances the accepted continuation and restores automatic loading. The source is still the same RecommendAPI; no source fallback or source/cursor mixing. Preserve current visible-row-derived idx semantics; do not invent a new server cursor from unrelated banner/ad rows. A valid continuation is the last committed usable row idx; an empty/null idx or unchanged continuation cannot generate an automatic request loop. Manual load more may retry the same idx after an empty/no-progress response. A failed attempt does not consume that idx. Remove the one-second duplicate suppression as a permanent retry gate; single-flight plus explicit automatic-load eligibility handles storms without blocking deliberate retry.

Refresh always requests `idx=0` and replaces committed rows/banner only after complete required parsing/mapping succeeds. A failed refresh leaves the same collection instance and row identities intact, preserving selection/scroll host. Successful refresh may intentionally replace rows and reset position. Retry dispatch remembers whether failure was initial/refresh or append; it must not infer mode merely from Items.Count. Loading resets in finally after state publication. Null/empty LoadMore and top-button activation are safe no-ops, including immediately after a failed/empty load.

Required feed validation: use existing ApiEnvelope `data` contract and actual HttpResults.TryGetJObject policy; code must be an Int32-range integer token, data an object, items an array, each required card entry decodable before publication. Missing/null/non-array items, null/invalid row, malformed code/body, transport failure, rejection and mapping exception become failures rather than empty successes. Empty array is success. Keep envelope/body salvage compatibility; do not globally alter HttpResults or scalar helpers. Preserve card models, title tooltips, ad filtering, `left_bottom_rcmd_reason_style` compatibility, browser/watch-later/dislike menus, banner-disable setting and optional banner tolerance. Prepare optional banner contents off to the side; a failed optional banner must not partially mutate committed banner or discard usable cards.

A small feature parser under `Parsing/Recommend/` is permitted if required to keep required payload validation/typed failures outside the VM; it must reuse existing envelope rules, not create a new transport framework. Any new file requires an explicit UWP Compile entry. R3 is a local returned-request selection correction. Action acknowledgement must still permit code0 without data; never apply feed data/items requirements to a dislike/feedback response. Preserve rejected-action rows and avoid treating a malformed code as action success, using the existing bounded business-code reader through a tiny feature action parser if necessary. No signer/API endpoint change is authorized.

## 3. Download read and cancellation ownership

### D1: completed-library scan

Retain `LoadDownloaded`/RefreshDownloaded caller compatibility (App startup, DownloadPage, settings path changes, Handel completion), using an awaitable Task core. Concurrent duplicate scan calls cannot clear/publish over one another; a busy request is coalesced or rejected without modifying committed rows. Busy spans the scan, not the lifetime of background downloads. Required root lookup/enumeration failure is caught/logged once, resets busy in finally, preserves exact prior Downloadeds and offers persistent read error plus RefreshDownloaded retry. Initial failure must remain distinguishable from successful zero media. XAML provides progress/empty/error/retry in the affected offline-video region.

Stage discovered rows, publish only once the required current-root scan succeeds. Preserve tolerant per-title/per-episode handling, extension filters, nonzero-media check, legacy metadata compatibility, sort order, playback/export models and paths. An unreadable/malformed child remains skipped; log its safe category and show one partial-read warning if any were skipped, rather than falsely reporting a fully clean empty library. Enabled legacy-root scan and disk-space metadata are secondary: a failure must not discard usable current-root rows. Retain/report that partial result, allow retry, and mark disk figures unavailable rather than showing fresh-looking zero/stale success. Do not redesign file enumeration or migrate schemas.

### D2: current transfer observer identity

`DownloadingItem.EpisodeID` is currently grouped CID, even for season tasks. Preserve that internal meaning; DownloadHelper's persisted GUID metadata stores CID and episode-folder Path. Do not substitute season episode id into cts keys or delete a parent video/season directory. Correct the SeasonDetailPage in-progress predicate to use the episode CID, matching this real row contract; its completed-download predicate continues to use persisted EpisodeID. No DownloadHelper schema/key migration is needed.

Repeated LoadDownloading scans must reuse the **actual CTS already bound to each active Handel/AttachAsync observer**, not merely an equivalent newly allocated CTS with the same CID key. At most one observer is attached per GUID. Each active GUID owns its stable cancellable observation; grouped CID cancellation enumerates only the immutable confirmed GUID set. Do not append a new GUID to a CTS that an earlier confirmation can cancel: per-GUID CTS ownership is the minimal required implementation. Sibling segments still cancel together by enumerating their confirmed sources; a genuinely new GUID/generation gets a fresh CTS even at the same CID/path. Retire/dispose an observer/CTS only after its owned operations settle; never detach an in-flight observer during list refresh. Keep per-operation GUID identity so late old completion cannot remove or cancel a new generation at the same CID/path. A scan gate covers discovery/reconciliation/publication only, never waits for all media transfers to finish before allowing the next scan. Enumeration/metadata failure is caught and keeps prior active rows/token ownership usable.

Delete requests must cancel every snapshotted current operation for the intended episode, covering multi-segment/DASH siblings and no other episode. Calling Cancel requests cancellation; it does not prove the transfer has rolled back or its folder has vanished. Use actual per-operation observations to bind any completion waits; avoid an unbounded global Task.WhenAll as deletion progress. Keep existing background transfer group/network settings and pause/start behavior.

### D5 / P1-RV1: shared preparation and cleanup path ownership

A point-in-time BackgroundDownloader scan is not an ownership transaction. Actual creation and every destructive caller must use one small process-local path coordinator; the coordinator itself is product code compiled into the real-source probe. It is an admission/ownership registry, not a new transfer scheduler. Use short synchronous registry updates plus disposable logical leases retained across the relevant awaits; never hold a monitor across an await or serialize unrelated episode paths.

**Path scope and admission:** resolve/capture the configured StorageFolder root once, then derive the existing video/season parent name (AVID or `ss`+SeasonID) and episode name (CID or season EpisodeID) without creating that episode. Normalize an absolute storage path consistently (Windows separators/case, directory-boundary-aware ancestor comparison); reject invalid/rooted/traversing child names rather than reserve one key and mutate another. Capture this path identity and use it throughout preparation. Obtain the episode preparation lease **before parent/episode creation or any auxiliary/media/metadata write for it**. The common default-root OpenIfExists step may precede admission because no authorized cleanup deletes that root. Different episode children, including siblings, remain independently admissible; a title-directory delete conflicts with every descendant episode reservation. An overlapping second preparation or cleanup receives a typed busy result before mutation; existing AddDownload Task failure handling makes retry possible. A creator arriving while a cleanup lease is active must fail safely before touching the path (or await its release without holding other path leases); the minimum implementation may fail fast. There is no unregistered fire-and-forget child that outlives the preparation lease.

The coordinator tracks a monotonic creation revision for the admitted episode path and for queries on ancestor subtrees. Every successful creator admission changes it before the first mutation, even if preparation later fails. A failed admission performs no path mutation. Capture cleanup targets while temporarily holding an exclusive snapshot lease on that episode/subtree: reject an already active/pending creator, reconcile actual current operation GUIDs/metadata, and capture the creation revision, intended immutable path/name/scope and GUID set. Release this snapshot lease **before** displaying confirmation; no lease is held across user think time. A confirmed cleanup reacquires exclusive ownership, rejects any preparation conflict/revision change, and reconciles current GUIDs again while holding ownership. Unknown/invalid metadata or failed enumeration is a typed reconciliation failure and fails that target closed; do not infer an empty operation set. Current owners must be a subset of the originally confirmed GUIDs. A newly published same-path GUID or any intervening admitted creator invalidates the old snapshot even if the new operation already completed or failed and no longer appears in a scan.

Keep this destructive lease from the final ownership/revision/operation checks through cancellation, awaited folder lookup and awaited DeleteAsync, including failure classification. New creators cannot mutate the path between the check and deletion. Capture the GUID-to-actual-CTS association through the observer registry; only confirmed still-current GUID sources may be cancelled. Per-GUID sources prevent a newly attached same-CID sibling at any path from inheriting an old cancellation. If any current ownership is unresolved, conflicting or unsnapshotted, report that target unchanged and return before **any** cancellation or deletion. Dispose every lease in finally on success, absence, permission error, preparation failure, reconciliation failure and synchronous launch failure. Process other episode targets independently; never acquire multiple path leases while awaiting one another. No lease spans a background media transfer lifetime.

**Actual helper preparation split:** preserve public `Task AddDownload(DownloadInfo)`, existing folder names, filenames/collision options, metadata schemas/settings keys, headers/group/network policies and optional cover/danmaku/subtitle tolerance. AddDownload must await all required child preparation and metadata publication, not just dispatch async-void work. Replace the private DownloadVideo async-void boundary with an awaited Task preparation method (or equally bounded helper) covering CreateFileAsync, CreateDownload, cost settings and GUID/DownloadGUIDInfo publication. Await SaveInfo and every outstanding child preparation until it either publishes the required operation/metadata or has a settled, reported failure. Required file/operation/GUID/manifest preparation failure must propagate to the existing caller catch (after all outstanding siblings settle); optional auxiliary failures keep their existing nonfatal log behavior. Already published siblings are retained/discoverable, not silently rolled back or deleted.

Invoke each prepared operation's StartAsync while preparation ownership still protects its admission/publication, then observe the returned transfer operation asynchronously through an exception-contained Task observer. Calling StartAsync to obtain its operation must occur before releasing preparation ownership; do not leave a post-release delayed launcher capable of starting writes after cleanup. **Do not await its media-lifetime completion in the preparation Task or under any path lease.** Synchronous launch failure is a settled preparation error; asynchronous transfer completion/failure is owned by the detached observer and actual VM/GUID lifecycle. AddDownload completion means required preparation/publication/start dispatch settled, not that the media finished. All asynchronous observers catch/log appropriately and cannot escape async-void. DownloadDialog already awaits AddDownload and catches failures at :201–210; allow minimal wiring/message adjustment only if needed to preserve truthful partial preparation failure and refresh discovered successful siblings. No dialog wait, command gate or path lease lasts through file transfer.

**Completed-delete bypasses:** actual DownloadPage has two additional PermanentDelete callers: btnEpisodesDelete_Click:284–303 (episode path) and btnMenuDetele_Click:344–362 (whole title/season path). Both must use the same snapshot/revision/exclusive path contract. A whole-title lease covers descendants and blocks admitted creators there, including a new episode absent from the old UI list. Completed-delete confirmations authorize removal of their named files, not cancellation of in-progress work: if current nonterminal operations or preparations overlap the scope, fail that delete safely with useful retry feedback; do not cancel those tasks. Preserve existing declined/success/storage-error behavior and list removal only after successful deletion. No local-media import/export, unrelated subtitle conversion or player redesign is added by this wiring.

## 4. Download command, file-effect and recovery contract

Use awaitable Task cores with exception-safe ICommand adapters. A command gate spans confirmation and operation; duplicate single/bulk activation cannot launch parallel confirmations/deletions. Release gates in finally for confirm rejection, exceptions and partial failure. Pause/resume remain per-operation controls; missing/completed operation is a harmless stale action, and a real platform failure is logged and shown once. Bulk start/pause continues other current targets and reports one aggregate failure summary, not one toast per segment.

Snapshot immutable target identity/name, original operation GUIDs/CID and episode folder path before confirmation. Single confirmation names title/episode and explicitly says cancellation permanently deletes files in that episode directory, including already received/completed portions. Bulk confirmation states exact snapshotted episode count and permanent deletion effect. Cancel/decline means no CTS cancellation, storage call, list mutation or automatic retry. Tasks added after confirmation begins are excluded. Capture requires the temporary coherent snapshot lease described in D5; acceptance reacquires a destructive lease and validates the captured creation revision. No filesystem mutation occurs on declined confirmation; the temporary snapshot does not cancel tasks or mutate rows.

After D5 admission/version/current-owner checks succeed under the destructive lease, confirmed deletion cancels the snapshotted actual per-GUID observers, then deletes only the intended episode folder with PermanentDelete. Treat already absent folder as successful cleanup once no conflicting active generation owns the path; access denied/locked/other failures are not success. A cancellation success followed by file failure must be reported as **task cancelled, partial files not deleted**, with count/target and recovery; do not claim the task is still resumable or that everything was deleted. A cancellation failure must not proceed to deletion while that transfer may still write. Continue independent targets in a batch, count success/failure per episode (not per media segment), log each failed target/category with exception, and emit one truthful summary. Keep full paths/raw exception text out of user-facing generic failure text; existing open-folder flow may expose the selected intended path.

Retain a persistent cleanup-failure snapshot after cancellation removes active rows, independently of real RemoveItem and future LoadDownloading rebuilds. Show the named failure, retry cleanup and an open-folder recovery action in DownloadPage; it need not masquerade as a running task. Retry addresses only this failed snapshot, reconfirms the permanent effect, and never silently restarts or recancels unrelated work. Before an initial, delayed or retried delete, use the shared D5 lease plus captured creation revision and actual current-transfer reconciliation. If a pending creator, changed revision or new GUID/generation conflicts, block stale cleanup before cancellation with actionable feedback. A cleanup retry keeps its original snapshot and cannot silently recapture new work as part of the old permission; cancelling newer work requires a separate fresh command/confirmation. A point-in-time scan or old row reference alone is insufficient. Success removes the cleanup failure; a second failure keeps it available. No universal undo is required.

Completed-download deletion already warns of permanent deletion, removes rows only after storage success and logs/toasts failure. Preserve those outcomes while adding the D5 shared episode/subtree lease and conflict checks to both actual handlers; keep local-media import/export/playback untouched.

## 6. Risks and native follow-up

Highest risks are accidentally changing feed filtering/paging, reporting cancelled files as deleted, reusing a cancelled CTS, and stale cleanup deleting a new transfer's files or cancelling an unsnapshotted same-CID GUID. Shared path preparation/cleanup ownership, immutable observer ownership and the separation of preparation from transfer lifetime close P1-RV1; final guarantees must be verified through the actual helper and page handlers, not a standalone gate test. The explicit publication/generation/snapshot tests above are mandatory. Keep new C# code compatible with the existing UWP project/compiler; net8-only convenience APIs in scratch are not production guidance.

Linux proves real-source control flow/parse/publication/token identity and primitive-failure recovery. It cannot prove BackgroundTransfer OS cancellation/file-handle release, real access-denied/file-lock behavior, XAML binding compilation/rendering, focus/Narrator or successful UWP startup. Windows follow-up for changed flows: compile `-Fast -NoVersionBump`; initial/empty/append/refresh failure+retry under delayed responses; confirm/decline single and bulk deletion; multi-segment cancellation, locked episode folder and cleanup retry; create another transfer at the same path before stale retry; scan an unavailable configured root then recover; verify completed downloads still play. Retain historical device acceptance and record these as touched-flow checks with SHA/OS/evidence, not fabricated new bug reports or fresh device PASS.
