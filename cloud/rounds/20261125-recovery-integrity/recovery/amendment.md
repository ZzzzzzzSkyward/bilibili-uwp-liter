## 1. RF1 — a failed cancellation stays unresolved for its current GUID

The existing cancellation-failure rule applies across commands: **no folder lookup or deletion while a cancellation-failed operation may still write.** Actual CTS.Cancel sets cancellation-requested before a callback throws; a repeat Cancel can succeed as a no-op. Keep failed-attempt knowledge per GUID and its actual attached source while that operation remains current, independently of a cleanup target/row. Neither retained RetryCleanup nor a freshly captured/confirmed DeleteItem/DeleteAll may forget that knowledge. Rescanning, a second CTS.Cancel, IsCancellationRequested, changing the primitive failure flag, removing a UI row or allocating a new target is not proof of cancellation.

Under the existing destructive lease, validate revision/current GUID/source ownership and unresolved failed cancellation **before any cancellation or storage call**. A current unresolved GUID blocks its target. Do not replace or detach the observer's CTS, recapture newer work into an old confirmation, assume a native file lock prevents harm, or wait indefinitely. Independent episode targets still proceed. Preserve all path admission/revision/reconciliation rules and actual observer lifetime ownership.

The block may end only on independently established operation settlement/disappearance (for example, successful current-group enumeration proves that GUID absent, or actual terminal operation evidence consistent with reconciliation), or an independently supported cancellation operation with established success. A Task/row retired solely because a requested CTS cancelled is not by itself new proof that a still-current failed transfer stopped. The minimal repair may simply fail closed while the GUID remains current and allow a later explicit retry after disappearance. An enumeration/metadata error is not absence. Retire failed-state entries only for their owned operation; late old settlement cannot clear a different GUID/source's failure.

Record each successful sibling cancellation as it happens, and retain a throwing GUID's unresolved result even if earlier siblings were cancelled. If a later sibling fails, delete no files; count one failed episode, retain its snapshot, and report that some tasks were cancelled/files remain rather than claiming the entire episode was cancelled or unchanged. All-success cancellation followed by storage failure keeps the original cancelled/files-not-deleted feedback. Confirmation, command/lease finally release and one aggregate batch report remain unchanged.

## 2. FA-02 — known unfinished remnants are not completed downloads

Keep a bounded **process-local** record of known cancelled unfinished episode paths whose cleanup did not finish, with normalized exact episode identity and creation/operation generation evidence. It must survive observer retirement, LoadDownloading rebuilds, a fresh command and stale CleanupFailures snapshots. Merely testing CleanupFailures.Count or whether any retained target contains the path is insufficient: old failures must not hide a demonstrably completed replacement forever. No new disk field/schema or restart guarantee is added.

LoadDownloadedAsync must withhold those episodes from completed publication even if every remaining media file is nonzero. Preserve the existing tolerant media/metadata/legacy rules for unrelated files; nonzero alone does not override known partial state and does not newly prove arbitrary files complete. An affected title may still publish its valid sibling episodes. A title made empty solely by withholding these remnants must not advertise a completed title; DownloadedStatus and retained recovery must truthfully explain partial/cleanup-pending content even when no completed episode remains. No cleanup target is silently discarded or recancelled by a read.

Use the existing normalized path/revision coordinator; episode containment is boundary-aware and case/separator consistent. Episode markers affect that episode, not sibling prefixes, other titles/roots or every descendant of a common title. For a cancellation scope containing several episode paths, classify the actual affected GUID metadata paths individually. Successful validated whole-title cleanup can resolve covered descendants; a known partial descendant must not hide an unrelated valid descendant. Same-CID different-path work remains independent.

Known-partial state clears/supersedes only on evidence bound to the affected episode/generation:

- Successful confirmed PermanentDelete or validated already-absent cleanup resolves the matching path/scope and applicable old failures. Absence is accepted under the existing revision/current-owner checks; unknown lookup/reconciliation is not success. A subsequent successful scan reflects the resolved state.
- A **newer admitted same-path generation** may supersede the marker only after its required preparation/metadata/SaveInfo/start dispatch succeeded and **every required operation in that captured generation completed successfully**. Track this bounded evidence through the existing AddDownload/transfer observer/coordinator paths; one completed sibling, an arbitrary discovered GUID, an observer's failure/cancellation, or disappearance alone does not establish replacement completion. Optional auxiliary failures retain their original tolerance. The successful evidence must still match the current episode revision and the scan's normal file/metadata checks.
- Admission/revision change alone, preparation failure before any GUID, partial preparation with a successful sibling, a pending/failed/cancelled replacement, or a new creator that has already disappeared must not turn old remnants into completed rows. Unrelated sibling creation must not expire the affected episode's marker. A later genuinely successful generation is publishable; its old cleanup snapshot remains stale and cannot delete it. Retire/identify that stale recovery state truthfully, without granting it new authority.

Recheck classification/generation before staged scan publication after asynchronous enumeration/file reads. A scan begun before cancellation or a replacement cannot publish its stale candidate over newer known-partial/pending state. A failed/old cleanup continuation cannot clear a newer marker or completion record. Keep locks short, logical leases across existing destructive/preparation awaits only, and no lease through transfer lifetime. Cleanup or a successful replacement permits a later truthful refresh; repeated scans must neither lose the marker nor poison the path permanently.

## 3. FA-03 — accepted row removal recomputes the owning feed state

Use the real Dislike/Feedback action and actual code0/no-data acknowledgement. Bind its target to the collection instance and row object used to build the request. On accepted acknowledgement remove that object only if that collection is still current and contains it; a completed refresh (including a replacement with the same idx) must not be altered by an old action. A missing target is a safe no-op. Rejection/malformed/transport failure retains the row and current feed state; request builders/signing/authentication semantics remain unchanged.

For a normal Ready collection, removing its final row yields Items.Count=0, `暂无推荐内容`, AutoLoad=false and a working refresh; LoadMore remains harmless. Removing a nonfinal row preserves usable rows/banner and valid continuation behavior. Recompute based on the **current feed request/state owner**, not an old action's captured Ready state: never enable automatic loading or overwrite a pending request, refresh/append failure/retry mode, or no-progress suppression. If a pending/intervening request fails after the removal, its error/actionable retry remains authoritative even with zero rows; retry initial/refresh/append mode is not inferred from the new count. Its later successful publication owns the resulting state normally.

## 4. FA-04 — finite progress with an unknown total

Actual GetProgress must return0 for total0, including received0 and received>0. Preserve ordinary0/10→0,5/10→50,10/10→100 and20/10→0 behavior. All ulong inputs produce finite values in[0,100]. Both LoadDownloading and DownloadProgress must publish that safe value through their existing real-method calls. Use UWP-compatible APIs; no ProgressBar/device-crash claim follows.
