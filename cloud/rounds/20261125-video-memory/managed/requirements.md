## Background and decision

The reported journey is about 50 open → watch → ordinary close cycles. Existing BR-21 and ROADMAP §1.1/1.4 require a managed/native split before global background-player work. This investigation found a reproducible late-close correctness defect in the season detail path, but no permanent page retention in the controlled, completed-operation close fixtures. The season defect requires closing while its initial detail/episode load is still pending; it is a race control, not reproduction of 50 fully watched items. It can be repaired independently of a player rewrite. The ordinary video detail path already rejects late page playback; its VM can still publish after close and launch the next related-video request, which is a transient retention/work candidate rather than proved permanent retention.

Evidence and limits are in [evidence.md](evidence.md) and [source-proof.md](source-proof.md). Scratch fixtures use exact product method bodies plus documented platform/transport doubles, optimized .NET 8 compilation, 50-cycle active-owner/ordinary-close/negative-close controls and weak references after creator methods return. They establish source behavior, not UWP/native object roots or Windows RAM.

## Proposed execution scope for M1 only

Goals: after an actual ordinary close, a season request may finish its transport operation, but must not publish metadata/episode lists, request the next detail substep, change a title, initialize media/comments/QR, or publish a stale error/loading state. A still-live page/player supports refresh and item replacement. The same VM may accept a new load generation, including after explicit invalidation. After terminal Page.Close/PlayerControl.Dispose, a legitimate user reopen uses a fresh page/player from the shell; no later entry may revive the disposed instance. In every case stale generation A remains rejected. An intentionally open page continues normal detail fallback, playback, episode/preview selection and error recovery. A reusable VM is not transplanted into a fresh page's x:Bind field.


The terminal-owner distinction follows root's [lifetime-decision.md](../lifetime-decision.md) and the actual shell/cache/refresh trace in [lifetime-reconciliation.md](lifetime-reconciliation.md). Tabbed open creates a new MyFrame; no-tab duplicate page type creates another frame; terminal Back disables the outgoing page cache and no-tab also clears its forward route/removes the extra frame. Multiwindow open creates a fresh view/frame. Forward-retained pages remain live, and Season's existing refresh/menu/error-retry handler reuses a live owner without Dispose. These are source preconditions, not native cache/Loaded acceptance. If Windows supplies a terminal instance on a supported path, capture that path and independently review a narrow routing/restoration amendment before widening scope.

Non-goals: native footprint reduction claims; global Player/PlayerControl ownership, SMTC or timer rewrites; stopping background playback merely on Unloaded, tab selection, visibility change or forward navigation; changing the transport-wide timeout; forced GC; broad cache eviction; per-video histories/playlist limits; VideoDetailVM changes; account/login/download/feed work; package/version/identity changes.

Minimal API/lifetime contract:

1. Keep the existing `LoadSeasonDetail(string season_id)` signature and normal caller semantics. Add an explicit VM operation such as `InvalidateLoad()` that advances its private load generation without requests, exceptions, UI notifications or implicit clearing of a still-active page's last good state. Beginning a new load also advances the generation. No static owner/global registry is needed.
2. `LoadSeasonDetail` captures the generation and holds response/mapping values locally until accepted. Check current ownership after each awaited metadata/decode/episode response, before starting the next request, before publishing any Detail/Episodes/Previews/visibility/Loaded state, and in catch/finally before changing error/loading state. Invalidated completion is a quiet superseded result. Normal active parse failures retain the prior good models exactly as existing season1 assertions require.
3. The page owns a closed latch plus a monotonically changing detail/open generation. `ClosePage` terminally invalidates this page and its embedded player lifetime, and invalidates its VM load **before** existing teardown/property changes/player disposal. Repeated close is safe. `InitSeasonDetail` captures the live page operation generation and checks it after its await before *any* title/review/player/comment/QR work. A new initialization on a live owner may advance its operation generation; reentry into a retained page that was never closed remains live. A freshly constructed page starts open, but a closed page's later Init/OnNavigated entry must preserve the closed latch and return before subscriptions, another VM request or UI/publication/player work; it must never clear the latch or restore player eligibility. VM `InvalidateLoad()` and a subsequent VM load are independently reusable, and do not reopen a terminal Page/player. Both VM and page generation checks remain required for stale and reverse-order operations.
4. Keep the existing subscriptions, `ReleaseShare`, `UnsubscribeClosedPage`, directory reset, fullscreen/miniplayer exit and player disposal. Do not cancel merely because an intentionally retained history page navigates forward or an open player unloads its visuals. Keep current x:Bind VM identity; replacing the whole VM field is not a substitute for generation ownership without proving binding reattachment.
5. No transport cancellation guarantee is added. A response already pending can still retain its await chain until the platform completes it; invalidation only prevents further work/publication. Do not advertise a hard memory/duration bound that source does not enforce.
6. Any newly touched `async void` page boundary must handle/log an active-operation exception; superseded completion is not a toast/error. Do not catch-and-ignore the reproduced null dereference as the repair.
