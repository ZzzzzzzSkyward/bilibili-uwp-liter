## Background and finding

The new report concerns memory after approximately fifty video open/watch/close cycles. BR-21 currently has no measured journey, process identity, before/after retained heap, or native allocation trace. A current checkout contains the actual large player/page sources, exact .NET 8 probe tools and portable Linux PowerShell; the historical sparse-source blocker does not apply. Windows UWP playback, VS, WPR and GPU execution are unavailable here.

The current diagnostic bundle records app version/session/capture switches/files; `Playback` logs record stage, engine/media type and open timing. Neither is a process memory sampler, object census, close-completion marker, player-owner ledger or session-ticket census. The ordinary `MainPage.ClosePage → MyFrame.Close → VideoDetailPage.ClosePage → PlayerControl.Dispose → Player.ClosePlay` path is distinct from tab hiding, minimizing and suspension. `PlayerControl.Dispose` releases media synchronously before its final history POST; that pending POST may temporarily retain the control. An idle wait must be recorded, not treated as guaranteed completion.

Current-source `PlayerSessionState` passed an isolated fifty-cycle resource-root experiment with active-owner controls; the existing unmodified owning probe passed 240 assertions. These results establish available regression seams, not UWP memory behavior or proof that all player/page roots are sound. No additional product defect or repair is proposed by the measurement workstream.

## Goals and non-goals

1. Produce a repeatable Windows observation with the same process and verified artifact: raw private bytes, working set, handle/thread/CPU values; action/state/checkpoint timestamps; exact controls; errors and availability.
2. Distinguish warmed allocation/caches and deliberate active playback from old closed owners accumulating; separate managed retained roots from native/media allocations and GPU surfaces.
3. Turn a reproduced owner-specific defect from the managed/resources streams into a deterministic actual-source regression. A fifty-iteration test and a Windows footprint trace remain separate evidence.
4. Preserve history, playlist, navigation, active/background playback, quality and engine fallback behavior.

Non-goals: a global player rewrite; new production GC/finalizer waits, working-set trimming or cache purges; silently disabling real media/danmaku work; changing package identity/version/signing/build configuration; claiming fixed RAM from Linux RSS, fake resources or source-string checks. Existing suspension GC is a confound to label, not a proposed fix or a reason to minimize the close-only test.

## Evidence levels and decision rules

| Level | Required artifact | Permitted conclusion |
| --- | --- | --- |
| E0 source hypothesis | Current caller/root/teardown graph with exact file/method | Candidate only; a self-owned object/event cycle alone is not a leak. |
| E1 deterministic actual-source ownership | Exact source hashes, executable fixture, active-owner control, ordinary close/replacement/late-result controls, operation/root observations, failing original and passing repaired source for a repair | Particular source ownership defect or bounded behavior under those dependencies; no Windows byte claim. Source-text assertions are wiring checks, labeled separately. |
| E2 Windows process trend | Verified package/artifact/PID+start time, fixed journey, raw checkpoints/samples, repeats/control, process identity continuity | Reproducible private-byte/working-set/handle/thread trend. No managed/native attribution solely by subtraction. |
| E3 attributed Windows retention | E2 plus matched managed snapshot roots or outstanding native allocations/stacks, or GPU allocation evidence; matching closed vs active owner and checkpoint | Attribute the supported allocation/root family. Missing symbols/providers or unsupported managed profiler means attribution unavailable. |
| E4 verified user repair | Same Windows fixture/artifact binding before and after repair, controls and native/playback behavior retained | The measured case improved/resolved within the captured conditions; no universal leak-free claim. |

Report raw points and interval slopes `(M_b-M_a)/(b-a)` for 0→5, 5→10, 10→25, 25→50, with immediate and settled/idle values separate. Record each run, then medians/ranges across three fresh-process repeats for suspicious journey and matched control. An increase persisting through late intervals/idle and recurring in repeats justifies attribution work. A plateau or fall after warm-up/idle weakens an unbounded-retention hypothesis for this fixture. Mixed/noisy signs mean inconclusive; do not invent an MB limit, confidence percentage, extrapolated leak size or coverage score. Deterministic old-owner/resource counts that rise with each closed cycle can establish a source regression regardless of an arbitrary byte budget. A working-set high-water line alone is not a retained-root finding.

## Required measurement fixture

The complete timed steps, executable checkpoint script and tool discovery are in [windows-protocol.md](windows-protocol.md). Every run fixes and records: viewport size/scaling/text size, window state, shell mode (tab/NoTab), account/session label without credentials, app/artifact SHA/version/architecture/configuration, device/OS/GPU driver, engine actually used, codec/resolution/quality/frame rate, playback rate/volume, subtitle/danmaku settings, autoplay/next-item setting, API-capture switches, network, entry route, starting media position and duration. No scrolling the feed/search while choosing the fifty videos. Use a prepared ordered list of media IDs/parts and a stable existing entry route; annotate failures, permission/quality changes and engine fallbacks.

Warm one common fixture identically in each fresh process: load the starting shell, open/watch/close five uncounted cycles of the same reference item, return to the same starting view, then idle sixty seconds. Record prewarm and warm0. This is a recorded warm-up, not an assertion that all caches are exhausted. Do not clear caches/GC/relaunch mid-run. A fresh-process repeat retains the ordinary installed application/disk cache state; record repeat order and cache state rather than claiming an artificial cold cache.

Required screening matrix:

| ID | Journey | Intent and expected owner state |
| --- | --- | --- |
| I | No interaction, same visible shell, duration matched to a fifty-cycle run | Background/time/logging drift control, no player owner. |
| F | Feed-only, fifty fixed scroll/page steps, no media; same timings/checkpoints | Feed/card/image growth control; count loaded cards/pages if observable, otherwise unavailable. |
| S | Same media/part fifty times, ordinary close each time, danmaku hidden | Separates repeated lifetime from distinct-content cache growth. Hidden danmaku is still data-loading work in current source. |
| D | Fifty distinct prepared videos/parts, ordinary close, danmaku hidden | Keyed content/history/cache variation; list/order fixed and hashed. |
| SD/DD | Same lists and timings as S/D, danmaku visible | Incremental rendering plus any data changes; settings and density recorded. |
| A | One deliberate active player while switching to a fixed non-player tab/view for a duration matched to S | Positive active-owner control; do not expect player/media roots to vanish. |
| M | One deliberate active player, minimize for sixty seconds then restore, repeat fifty times if screen/repro needs it | Background/suspend control, separate from close. Record suspend/resume markers and any existing GC. |

Run I/F/S/D/SD/DD once for screening; repeat the suspicious case and its closest control three times in fresh processes before E2 trend claims. Run A whenever managed root/resource interpretation is attempted; run M separately when background behavior or visibility could explain the report. Test one engine first; record actual fallback as a deviation, then run a separate fixed-engine fixture if needed. Do not combine browser/network failures, local media, live rooms, season playback, engine changes, minimize or app exit into the primary S/D series. These can be scoped follow-ups.

Checkpoints: prewarm, warm0, cycles 5/10/25/50 while playback is active, immediately after actual tab/back close, after ten seconds in the starting view, then final idle60 and idle300 with no player. A background run records minimized/background/restored states instead of pretending they are closed. Continuous two-second process sampling is desirable; checkpoint sampling remains a truthful fallback with lower time resolution. At every cycle record open request, media actually started, close action, starting view returned and any failure; at checkpoints record observed tab/player-owner counts and available object/resource cardinalities.

Thirty seconds of actual playback per cycle is the default (starting at a fixed zero/seek-reset position); ten seconds between close and next open. Media must have enough duration to avoid autoplay completion. Manually reset resumed history position before timed playback and mark seek completion. Mark the attempted and completed cycle counts separately. A load failure is a recorded failed attempt, never silently substituted as a successful fifty-cycle completion; fixed timeout is sixty seconds. Exact starts/timeouts/deviations appear in the manifest and events.

## Required data and collection API

Store raw captures outside the repository in a dedicated fresh run directory. `metadata.json`, `samples.ndjson` or `checkpoints.ndjson`, `events.ndjson`, `objects.csv`/`allocations.csv` when available, raw profiler/ETL files and a small summary comprise one run. UTF-8, invariant JSON numbers, UTC ISO8601 and monotonic ticks/frequency; bytes are integer bytes, never rounded MB. Unknown measurements are null with status/reason; zero means measured zero. Read CLR getters through an exception-propagating accessor (the fallback uses reflection), reject a raw null result before numeric conversion, and preserve empty collections/true zero. PowerShell adapted-property access followed by a numeric cast is insufficient: a throwing getter can become null then a false zero even with strict mode and ErrorActionPreference Stop.

`metadata.json` schemaVersion 1: runId, evidenceLevel, createdUtc, sourceCommit (or unknown), sourceDirty, artifactPath/hash, appVersion, configuration, architecture, effective runtime/toolchain, packageFullName/familyName/appId/executable from the installed manifest, observed process ID/start/path and verification method, OS/build, RAM, CPU/GPU/driver (or unavailable), power/display/scaling, shell/account label, network label, media-list hash/order, requested and actual engine/quality/codec, all fixture switches, durations/timeout/warm-up, profiler mode/version, script hash/version, outputs and deviations. Do not store credentials, cookies, API responses, user IDs or process command lines by default.

Process record schemaVersion/runId/sampleSequence/utc/monotonicTicks/stopwatchFrequency/processId/processStartUtc/privateBytes/workingSetBytes/handleCount/threadCount/cpuTotalMs/status/errors. Refresh the `System.Diagnostics.Process` before reading. `PrivateMemorySize64` is Windows Private Bytes (private committed memory); `WorkingSet64` is resident shared+private physical pages, not private commit. Do not use peak fields as current values or sum shared working sets across unrelated host processes. Target PID plus start time is mandatory; exit/restart/reused PID ends that run, records the identity error, and requires a new run directory.

Event record schemaVersion/runId/sequence/utc/monotonicTicks/cycle/phase/action/completedCycles/mediaLabel/mediaPart/actualEngine/actualQuality/windowState/visibleTabs/observedPlayers/status/note. Both checkpoint interfaces accept the same explicit phase set: `prewarm`, `baseline`, `opened`, `post-close`, `settled`, `idle60`, `idle300`, `background`, `minimized`, `restored`, `feed-step`; invalid phases fail before dependency reads/output. Predeclare expected fifty cycle IDs; failed/time-out/incomplete/active/suspended must stay distinguishable. Tool markers never claim UI automation or verified close completion: the operator records observed state; a future product marker would require a separate reviewed owner grant.

Object/resource census: checkpoint, family/type, count, shallow/retained bytes where supplied, root/allocation-stack reference, owner IDs/state, sourceTool/evidenceLevel, availability/reason. Relevant families: VideoDetail/Season/LocalPlayer pages and VMs, MyFrame/tab/backstack, PlayerControl/Player/BiliPlayer, session tickets/held resources, live timers and event subscriptions, pending open/history/subtitle/danmaku operations, MediaPlayer/MediaSource/FFmpeg media sources/streams, danmaku pool/model/rendered item counts, feed cards/images/cache entries, OS handle/thread counts. Counts require actual profiler/debugger/test observations; a process cannot enumerate managed tasks, danmaku items or media objects through `Get-Process`. Do not install a production strong-reference registry to count them. Inclusive retained sizes overlap and must not be summed.

## Actual-source regression boundary

Extend the existing owning probe for any independently confirmed defect, preserving every original assertion. For session-only cases `plan/tests/playersess` already links actual `PlayerSessionState`; its player/control source checks do not execute XAML/native code. Current scratch proof supplies fifty pending-close/late-resource and fifty accepted-owner-close cycles with a live-owner positive control, exact-once disposal, weak root checks at 5/10/25/50 and no test-local resource roots after no-inline factories return. A mutation retaining the disposed resource list makes the same fixture fail. This is an operational seam, not an assertion that UWP pages or native media were instantiated.

For any proposed repair the failure must be in actual affected source/call ordering, with the same fixture/source selector demonstrating original failure and repaired success. Scheduler/event/task fakes may control dependencies, but do not copy/reimplement the owner method. Include close while open/danmaku/history work is blocked, completion/failure/cancellation and replacement/late completion as appropriate. Maintain one intentionally active owner until explicitly closed; prove no cleanup prematurely breaks it. Observe rooted survivor/held-operation counts or exact resource release rather than RSS, arbitrary elapsed waits or `GC.GetTotalMemory` thresholds. Weak-reference checks use bounded test-only collection after local/async roots are released, with no-inline factories/finished tasks and documented JIT controls. Test-only GC is never inserted into the application. A general-purpose fifty-cycle session test is optional prevention, not a prerequisite to claim a source fix for an unrelated owner.
