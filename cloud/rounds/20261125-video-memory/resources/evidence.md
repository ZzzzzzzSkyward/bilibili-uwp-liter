## Findings that support a narrow repair

### R1 — confirmed post-close subtitle timer creation; P1 lifecycle defect

`PlayerControl.xaml.cs:2425` `GetPlayerInfo` awaits `playerHelper.GetPlayInfo` at2513, then updates the subtitle menu and calls `SelectInitialSubtitle` at2528 without checking the original play item or `_playItemGeneration`. `SelectInitialSubtitle:1693` calls `SetSubTitle:1758`, which starts a **new** `_subtitleLoadGuard` generation. A returned subtitle at1769–1788 therefore passes the new guard and starts a100ms `DispatcherTimer` even if close already invalidated the previous generation and stopped the previous timer in `Dispose:3920`.

The existing caller check in `SetPlayItem:1612` happens **after** `GetPlayerInfo` returns and cannot undo its timer. The existing guard correctly rejects a subtitle request already pending at close; the defect is a new request/ticket minted by a late upstream continuation. `CurrentPlayItem` stays non-null at disposal, so item identity alone does not detect close. The timer's instance `SubtitleTimer_Tick` delegate points back to the closed control. A live dispatcher timer is the hypothesized platform root; finite request/task retention alone is not being called a leak.

Actual-source extracted methods + actual linked guard/session classes reproduced50/50 closed controls surviving under an explicit dispatcher-root model. Active control, ordinary close, empty-result close and subtitle-already-pending-at-close controls distinguish this route. Clearing the test dispatcher root then releases every survivor. This is a confirmed source lifecycle hole and a modeled managed-retention mechanism; it does not establish UWP dispatcher/root counts or bytes on Windows.

### R2 — confirmed post-close playback-session creation; P1 lifecycle defect

`SetQuality:2328` captures only `requestedItem` before awaiting `GetPlayUrls:2348`; its2350 check compares item identity only. `Dispose` invalidates `_playerSessions` and increments `_playItemGeneration` but does not clear `CurrentPlayItem`. A successful delayed quality response therefore reaches actual `ChangeQuality:2564`, which calls `_playerSessions.Begin(QualityChange):2572` **after** close. Its new ticket is current, and the actual method proceeds to an engine open. Invalidating the earlier ticket cannot invalidate a ticket that does not exist yet.

The extracted real `SetQuality`, `ChangeQuality` and `Dispose`, with engine boundaries stubbed, produced50 post-close open calls and50 new accepted session ids in50 cycles. The engine stub deliberately accepts the real ticket and returns success; it does not allocate a native player. This proves the source caller/session ordering defect, not the number or size of leaked native allocations. Actual media methods do allocate/publish players/sources for a current ticket; see ownership below. `Player_PlayMediaOpened:3860` remains wired after disposal and can run auto-play if a late fresh session opens, increasing the importance of rejecting creation rather than only hiding UI.

### R3 — confirmed repeated owned-handler accumulation; P2 bounded-lifetime work amplification

Every `PlayerControl_Loaded:439` calls `LoadPlayerSetting:915`, `LoadDanmuSetting:776`, and `LoadSutitleSetting:998`. These append anonymous handlers on child controls every time; they do not detach or guard the additions. The exact extracted subtitle-setting method, called50 times on one owner, produced50 `SubtitleSettingBold.Toggled` subscribers and50 `UpdateSubtitle` calls for **one** subsequent toggle. Dropping that owner then collected it: retained controls0. This is not a global event leak across50 newly constructed players. It is increasing work/delegate storage while the **same** retained player is loaded repeatedly; subtitle refresh can multiply image generation. The other two methods have the same visible append pattern but were source-inspected, not executed in this fixture. Whether the user's particular50-video journey reloads one instance is not known.

### R4 — confirmed conditional teardown abort; P2 error-path hole, occurrence unproven

Exact extracted `Player.ClosePlay:1713` successfully detaches both elements, disposes both native-player wrappers once and clears fields on ordinary close; calling it twice is harmless under nonthrowing boundaries. If the **first** FFmpeg `Dispose` throws, no catch/finally protects later disposal: the audio FFmpeg source and both media players receive zero disposals, and the exception escapes. The field being disposed is nulled only after successful disposal, so a later retry may fail at the same place again. `PlayerControl.Dispose:3942` calls `Player.Dispose` before stopping history/danmaku timers or clearing the pool, so an exception can skip those later operations too. Real WinRT/FFmpeg teardown exceptions were not observed here. Keep this separate from an ordinary successful-close leak.
