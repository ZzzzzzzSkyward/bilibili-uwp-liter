## Background and goal

The user reports increasing memory after roughly50 open/watch/close video cycles. Current ordinary `Player.ClosePlay` does detach/dispose players and FFmpeg sources; existing session guards correctly release obsolete **already-created** opens. Two actual-source holes can nevertheless start new work after disposal: delayed `GetPlayerInfo` can create a new subtitle guard/timer (R1), and delayed `SetQuality` can create a new current player session/open (R2). Exact50-cycle fixtures distinguish those failures from intentionally active owners and ordinary close. Repeated settings-handler attachment on one reloaded owner is also proven (R3), but is distinct from retaining50 closed controls.

Goal: prevent closed/replaced playback work from creating or publishing resources and prevent repeated loads from multiplying settings handlers, while preserving the established player/session/history/background behaviors. Obtain native measurement separately before declaring the user's reported memory growth reproduced or fixed.

Non-goals: global player/background/SMTC rewrite, changing decoder/quality selection or playlist/history policy, treating normal self-cycles as leaks, forced production GC/finalizer waits, cache purge, timers stopped merely because an active player becomes invisible, changing credentials/schema/version/identity, or repairing every source-visible native lifetime uncertainty without an ownership proof.

## Lifetime, API and data contract

1. **Dispose is terminal for one PlayerControl instance.** Set its monotonic terminal latch before callbacks can mint sessions/track guards. `InitializePlayInfo` and `Loaded` on a disposed owner must quietly return before any resource/global-binding work; neither may clear/reset the latch. A later legitimate open gets a fresh constructed page/XAML PlayerControl through the actual new-frame/noncached caller paths documented in [RR1-lifetime.md](RR1-lifetime.md). No same-instance restoration is promised or authorized; this matches root [lifetime-decision.md](../lifetime-decision.md) and the managed caller reconciliation. An undisposed owner may initialize/replace its item repeatedly, including the same PlayInfo reference/id, by advancing its operation generation. Unloaded/minimize/tab visibility and retained live-history reentry do not imply Dispose. Unloaded must still detach its existing view bindings after close.
2. The current API remains `InitializePlayInfo(playInfos,index,start)`; a live caller must first validate its **captured original page/navigation/detail operation identity** immediately before calling it. Existing VideoDetail page checks remain; managed M1 owns the corresponding season checks. The player cannot turn an old caller into fresh authorization by recapturing current state or resetting terminal state. Capture immutable expected owner/item identity and generation **before** each asynchronous producer starts. After every relevant await, verify that identity/generation/lifetime before changing fields, setting menus, starting subtitle/danmaku work, changing interaction state, showing errors, or creating/accepting a new engine session. Checking only the caller after the whole child operation completes is too late. Checking only `ReferenceEquals(CurrentPlayItem,item)` misses close; checking only the currently minted session misses R1/R2.
3. At minimum cover actual `SetQuality→ChangeQuality` and `GetPlayerInfo→SelectInitialSubtitle→SetSubTitle` proven failures. Audit every route that can call these or mint fresh guards after another await (`ChangedNode:1948`, picker completion/import:4126–4217, local track rollback/reopen:2017–2098). A common live-lifetime entry gate is allowed to close analogous routes without a rewrite; each additional changed route requires a real method fixture/control. Do not silently claim unexercised routes fixed.
4. Keep `PlayerSessionState` Begin/Hold/Accept/Invalidate/Abandon/Release meaning and `PlayerToastService` semantics intact. Accepted native resources remain owned by Player fields and are released by ClosePlay; pending resources born late must still be disposed exactly once. Successful quality/fallback operations may legitimately create new sessions during a live lifetime. Old failure paths must not release a replacement's resources or trigger a fallback/error after close.
5. Keep initial subtitle choice/AI preference, manual subtitle choice, local manifest/download/import behavior, surface visibility and latest subtitle ticket semantics. New work only applies to its captured current item/generation. Late info for A must not mint a newer subtitle guard for B or replace B's selection.
6. Repeated Loaded may re-read persisted settings and reflect changes made elsewhere, but each logical control event has one registered behavior per owner. A bool that skips **all settings refresh** after the first load is not an acceptable duplicate-handler fix. All three settings initializers share the same rule. Retain the active owner's expected setting write, render update, ratio/rate/volume and toast behavior.
7. Preserve history key, synchronous local position save on dispose/flush, serial latest pending report drain, conditional remote report and pause/end/manifest behavior. Preserve the constructor-created history timer's once-only Tick registration and stop-on-close contract. A fix must not turn close into an unbounded wait for HTTP or discard the last saved progress.
8. No API result/schema/request change is required. The expected new data is internal playback lifetime/current-work identity only; no serializable state or persisted flags. Stale completion is a quiet no-op (with existing diagnostic logging if useful), not a playback failure toast.

## Secondary findings and repair gate

- **R4 conditional cleanup abort:** first FFmpeg.Dispose exception prevents later player/source cleanup, and can prevent PlayerControl timers stopping. The exact method fixture demonstrates this with one injected fault; native occurrence is unproven. If added to scope, require best-effort independent release, fields detached/cleared even on a failing releaser, idempotent close, exactly-once attempted disposal where intended, cleanup of all later resources/timers and no exception escaping async-void close. Do not let stale cleanup close a replacement. Run nonthrowing and per-resource fault cases on the real method; do not require a universal swallowing of unrelated programming errors.
- **Adaptive/native/local streams:** explicit ownership is incomplete in source, but async/native component lifetime rules must be verified before disposing clients/streams/sources. No source-based claim of accumulating native bytes. No shared transport changes on this finding alone.
- **Win2D subtitle temporaries:** explicit disposal is absent for five per-render types; the shared CanvasDevice is not owned per cue. A scoped deterministic-disposal change could be reviewed later with actual-method success/failure ownership fixtures and Windows subtitle visual acceptance. It is not evidence that these wrappers never finalize or explain the50-video report.
- **DisplayRequest:** RequestActive/Release balance is untracked and Dispose nulls the wrapper. Measure/verify screen-awake semantics; do not infer managed heap leakage. Any fix must preserve active playback and release exactly the requests acquired by this owner.
- **NSDanmaku:** package internal timers/render-target/unload policy unavailable locally. Pool/task/snapshot growth must be measured by current active workload. Avoid speculative ClearAll-on-hide or forced renderer destruction that breaks background playback.
