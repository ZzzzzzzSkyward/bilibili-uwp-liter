The immediate defect is in existing comment actions: a raw CSRF token is appended to another form field. Correcting that request construction is the first safe executable slice. ## 6. PB1 follow-up: typed failure for an out-of-range business code

### 6.1 Observed result, not a hypothesis

The supplied `parser-boundary-input.md` asked for `{"code":2147483648,"data":{}}` and its negative counterpart. The actual product source was compiled into a scratch net8.0 console project using the verification stream's SDK 8.0.427 and Newtonsoft.Json 13.0.3. For each of `ApiEnvelope.Read`, `ReadResult`, `VideoEnvelope.ReadDataToken` and `WebCommentActionParser.Parse`, codes `2147483648` and `-2147483649` **threw OverflowException**. Integer values `9223372036854775808` and `-9223372036854775809` **threw InvalidCastException**. The process returned 1 for **16 contract violations**. Int32.MinValue/MaxValue and -404 retained Rejected, business code and message; ordinary zero/empty-object cases and action success without data succeeded. Exact project, program, source hashes, command and output are in [source-evidence.md](source-evidence.md).

The HttpResults seam only parses complete JSON objects; it does not implement any code conversion. This isolates the defect in actual reader code. It does not prove a server sends these values, nor any app/device exception outcome. Existing comments fixtures (`Program.cs:145–167,409–441`) cover absent/string/nonzero code but not integer range; the same searched fixtures were absent in c1/season1.

### 6.2 Narrow design boundary and expected files

Keep the typed business-code contract Int32. Add a single bounded **integer-token code reader** within the existing `Parsing/ApiEnvelope.cs` (an internal helper can avoid expanding public API). Reuse it from the existing ApiEnvelope payload reader, `Parsing/Video/VideoEnvelope.cs` and `Parsing/Comment/WebCommentActionParser.cs`. The helper must reject missing/null/noninteger tokens and any integer outside Int32 without throwing, including Newtonsoft BigInteger representation beyond Int64. Do not widen `BusinessCode` globally, coerce a string/float to a code, truncate/wrap/clamp a code to zero, duplicate three subtly different range policies, or catch all caller exceptions as transport failure.

Preserve each endpoint's payload and message handling: ApiEnvelope still chooses data/result object explicitly, VideoEnvelope still returns raw/possibly absent data for its caller, and comment actions still allow no data at all. Code validation and in-range business rejection stay before payload validation. This is shared error-boundary hardening, not a parser migration or account change.

## 8. Risks, triage and handoff

- **Encoding regression:** ReplyComment already receives escaped text, AddComment receives raw text. Moving encoding wholesale into the builder without changing both callers double-escapes replies. U1 acceptance pins the current interface and keeps caller files out of scope.
- **Authentication overclaim:** an explicit CSRF field and `need_cookie=true` are insufficient evidence of outgoing WinRT cookies. Keep form proof and session/transport proof as separately recorded gates.
- **Historical documentation drift:** P4 inventory's opening overview and refresh-plan findings describe earlier baselines; its completion rows and current source supersede them. ROADMAP's tip/count and sparse notes are historical; source/intake evidence is current. Do not blindly reopen migrations or invent missing-source failures.
- **Measurement versus fix:** SMTC ownership, forced finalization and stale persistence aliasing are different causal questions. Reproduce or measure each; avoid a broad player/storage/transport rewrite justified by one memory report.
- **Shared ownership:** E1 overlaps the UX stream; U5/U8 share SearchAPI; all shipped-slice dispositions share PLAN/ROADMAP/VALIDATION. The orchestrator must assign one writer per shared file, with sequential execution or one combined reviewed ownership scope.
- **Completion:** passing requirements review authorizes only the assigned implementation slice. Independent implementation review must check the actual diff, before/after probe evidence and blocked gates. No terminal PASS should imply Windows runtime success from console tests.

At each maintenance cycle, triage new BR/logs into transport, server rejection, malformed response, state ownership, persistence or UI; attach sanitized request ID/endpoint/stage and a reproducer. Pick one confirmed executable defect; preserve accepted feature status. Re-run only affected behavior batches after the first full baseline, update the owning plan/disposition, and carry blocked checks with an exact prerequisite and next action. Repeat device memory measurements with the same journeys and intervals before comparing trends. The orchestrator's canonical maintenance plan should retain U1→PB1→U9→U5→E1 as available safe work while U2/player/account prerequisites are resolved, and include U8 under exclusive SearchAPI ownership.
