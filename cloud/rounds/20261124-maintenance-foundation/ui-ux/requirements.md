## 1. Background, goals and boundaries

Users primarily want to discover something to watch, play the intended item with working controls, resume or continue a queue, interact with comments, watch live chat, maintain a session, retain media for offline use, and recover from failures without losing their place or work. These needs follow README:13–23, the entry navigation in `Pages/HomePage.xaml:7–130`, and the current feature index. A third-party Windows media client does not need every endpoint offered by its sibling to satisfy those needs.

The maintenance goal is reliable completion and recovery of these existing journeys. Prioritize the confirmed comment-write defect U1; then triage source-visible recovery gaps, actionable names and narrow-window states in small reviewed slices. Preserve existing navigation, settings ownership, user text and media-session contracts. Record real failures separately from unsupported assumptions about layout or server behavior.

Non-goals: visual redesign; replacing Pivot/TabView; replaying completed card/settings/playlist milestones; creating a new login protocol or account-parser migration; player-class/SMTC rewrite without measurements; global request pacing changes; adding private messages, lottery operations, new media formats, live tiles, real BUVID acquisition, alternative danmaku renderer or other parked features; release/publish/master changes.

### Acceptance policy and environment

- `plan/VALIDATION.md:6–12` explicitly says shipped device rows count as passed and are optional confirmation; only an actual report recorded as a new BR reopens a shipped item. Its later historical “needs device pass” wording and ROADMAP device lists must not silently reverse that policy. Keep current accepted features accepted. Proposed scenarios below describe regression checks for future touched code, not a newly imposed gate on every shipped feature.
- This audit does **not** establish current device success. New or changed playback/layout/account outcomes still require maintainer evidence before the agent claims those outcomes verified (`AGENTS.md` verification gates).
- Current machine is Linux, with no `dotnet`, `powershell` or `pwsh` on PATH at audit time. UWP build, Narrator, text scaling, focus rendering, playback, Store file pickers and real session tests were not attempted here.
- Historical sparse-clone restrictions remain a rule against changing clone configuration or retrieving excluded blobs. However, `intake.md` and this audit confirm `PlayerControl.xaml.cs`, `DynamicVM.cs` and `VideoDetailPage.xaml.cs` **are present** here. Their old absence is not a current blocker or excuse to skip source inspection.

## 4. First executable slice: restore correct comment-write requests (U1)

This is a shared logic/UX slice, not a parallel duplicate implementation. Use the logic stream's reviewed contract for implementation and test ownership. This stream's concrete user acceptance is below.

### Goal and request/data constraints

- With a nonempty session CSRF token, Like, ReplyComment and AddComment produce one explicit `csrf` form field, separate from `type` and `message`. Like retains oid/rpid/action/type; reply retains oid/root/parent/type/message; add retains oid/type/message.
- Preserve current calling convention: AddComment receives plain text and URL-encodes it once; ReplyComment is called with already encoded text from `CommentControl.xaml.cs:523,569`. Do not double-encode that reply, decode user payload before request, or add a second escaping step without changing all callers under an approved contract.
- Preserve Chinese, line breaks, ampersand/equal/plus/percent/hash characters and non-BMP emoji. Form decode exactly once must recover intended text and IDs. Test literal text resembling form fields (e.g. `a&csrf=other+b%`) so content cannot turn into a second form key. Use dummy credentials only.
- DeleteComment already has explicit csrf (`CommentApi.cs:109–119`); verify it remains correct as regression. Do not “fix” it by assuming every GetCSRF caller is broken. Preserve endpoints, verbs, action values, comment types, existing cookie flow and sign/transport behavior.
- The behavior for absent token must follow the logic review; no successful request or login state may be fabricated. Authenticated UI paths already reject logged-out operations (`CommentControl.xaml.cs:368–377,509–519,616–620`). Do not change session storage or credential ownership to solve a form defect.

### Measurable acceptance

1. Offline behavioral probe compiles **real** `CommentApi.cs`, constructs each affected request with a dummy token, splits/decodes form fields and asserts exact keys/values, one csrf, unchanged type and message, encoded reply convention and delete regression. The existing `comments` project currently links parsers/models only (`CommentsProbe.csproj:17–27`); add request coverage to its owner rather than claiming parser assertions cover requests.
2. Repeat above for comment types used in video and dynamic flows; include multi-digit action/type/ID values and Unicode/punctuation text. No real network, no secrets, no test-only reimplementation of the builder.
3. Existing comments parser probes continue passing; compile on Windows via `build-release-x64.ps1 -Fast -NoVersionBump` (and restore when needed), zero errors. Environment failure is recorded as BLOCKED/FAILED with command output, never pass.
4. Optional maintainer confirmation for the changed area: in an authorized session/test-owned content, like once/unlike once; post top-level text containing `中文 & + = % 😀`; reply to root and nested reply; refresh and read exact text/parent; delete own test comment. Only server-accepted responses change visible count/state or report success. Capture version/time, sanitized request shape and outcome, never token/comment contents from a private report.
5. A server rejection/network failure remains reported as failure under existing UI; U1 alone does not claim to solve dialog retry/draft retention. Record UX-02 as separate follow-up. Do not silently broaden the request slice to UI lifecycle or add undocumented live writes.

Expected modification surface after PASS: `Api/CommentApi.cs`, existing comments probe project/program or a narrowly owned real-source helper if agreed by logic reviewer, plus backlog/review/validation records assigned to one documentation executor. No XAML, global ApiHelper, credentials, player, manifest, assets, live JSON, settings or protocol changes needed for U1. Requirements owner writes none of these.

## 7. Risks, cadence and closure

- Highest risk is changing shared CSRF/encoding semantics or session state while fixing a local form; confine U1 to the affected builder and true calling convention. Unicode/encoded payload tests are mandatory for that slice.
- Layout/accessibility observations can be distorted by XAML default templates, automation peers, tooltips, theme resources and OS scale. Escalate source leads with a concrete UIA tree/screenshot before claiming runtime defects. Keep privacy sanitization in existing services and do not copy private payloads into evidence.
- Old plans contain historical proposed layouts, retired controls and old commit tips. Current source and explicit device-acceptance policy take precedence. Feature completeness is not “no gaps”: section 3 records remaining recovery/accessibility work without relabeling implemented bulk/import/export operations as absent.
- Triage each new BR with version/time/journey/expected-actual, log marker and smallest safe reproduction. Rank failure to complete an existing action above cosmetic consistency. One reviewed owner/slice per change; parser/session/credential invariants remain explicit. Store recurring maintenance instructions as a cadence, not an automatic scheduled task.
- On each merged behavioral change: run its owning probes, perform applicable compile gate, and update the exact touched device scenario. Weekly maintainer triage: review new BRs, count unresolved P0/P1 and retry/draft-loss reports, identify one root cause/owner. Monthly or before release: the bounded core-journey smoke and BR-21 measurement only when new evidence warrants it. Track time-to-recovery and unresolved failures, not just number of UI controls annotated.
- Per-slice closure metric: zero unresolved P0/P1 introduced by the slice, 100% of specified offline assertions passed or explicitly environment-failed with command evidence, and every required device outcome either evidenced or explicitly BLOCKED/FAILED. Baseline runtime status from historical accepted rows is not represented as fresh verification.
- This stream is ready for review and U1 synthesis. It does **not** conclude “no functional or usability gaps”; UX-02–06 remain concrete triage records. Do not claim the repository-wide contract stop conditions are met while Windows build/runtime and measured issues lack current evidence. The orchestrator assigns documentation ownership and terminal status; no requirement owner alters root documents or git history.
