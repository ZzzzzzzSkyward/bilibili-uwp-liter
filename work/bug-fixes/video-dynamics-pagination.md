# Video dynamics 404 and repeated pagination

The user supplied logs show a failed `dynamic_history` request returning HTTP 404, followed immediately by another history request returning HTTP 412. In both cases the request method is GET and the failures arrive within milliseconds. This confirms that the video feed continues auto-pagination after a failed history fetch; it does not establish whether the original 404 endpoint failure is caused by endpoint retirement or another request issue.

The pinned sibling at `ca2caddc597b3faf05b4dac6dcb226aa0694365b` has the same empty-scroll behavior in `src/BiliLite.UWP/Controls/MyAdaptiveGridView.cs`: the `Loading` property callback invokes `LoadMoreCommand` when `ScrollableHeight == 0` without checking `CanLoadMore`. The scroll position callback does check `CanLoadMore`, but the sibling video page hard-codes `CanLoadMore="True"`. The sibling home video view model's `finally` sets `Loading = false` after an error, so an existing short list can trigger another request with the same final dynamic ID.

The sibling's source-backed current feed path is gRPC `bilibili.app.dynamic.v2.Dynamic/DynVideo`. `src/BiliLite.UWP/ViewModels/Home/DynamicPageViewModel.cs` calls `GrpcService.GetDynVideo(page, historyOffset, updateBaseline)`, then maps `DynVideoReply.DynamicList.List` using `MapToDynamicItemModels()` in `src/BiliLite.UWP/Extensions/MapperExtensions.cs`. The mapper converts protobuf `DynamicItem` card types and modules to the current grid's `DynamicItemModel`. The request and response types are `DynVideoReq` and `DynVideoReply` from `Bilibili.App.Dynamic.V2`; the sibling includes their definitions through `src/BiliLite.gRPC/bilibili/app/dynamic/v2/dynamic.proto` in its gRPC project. Pagination uses `Page`, `RefreshType.History`, `Offset`, and `UpdateBaseline`; the response supplies `HasMore`, `HistoryOffset`, and `UpdateBaseline`.

The sibling still retains `DyanmicNew` and `HistoryDynamic` as the web fallback for its video page. Its polymer `feed/all` usage (`DynamicAPI.ArticleV2`) is wired to article cards (`ModuleDynArticles`), and no sibling caller demonstrates that endpoint for the home video feed. `SpaceHistoryV2` is a different space-history endpoint and has no caller in the sibling tree. Therefore there is no source-supported polymer replacement for this video feed. The target currently has no Dynamic v2 proto types or `GrpcService`; adopting the sibling gRPC path requires a separate bounded proto/service/mapping port.

The target pagination fix binds the video page's `CanLoadMore` to `DynamicVM`, makes the control property a dependency property, and gates all empty-scroll/near-bottom triggers on that value. The VM clears it while a request is active and leaves it disabled after transport, API, or parsing failure. Explicit refresh clears the failed-page state and starts again from the latest feed. No cooldown, retry loop, or endpoint behavior is added.

## gRPC feed integration

The target home video Dynamics view now calls the sibling-grounded `GrpcService.GetDynVideo(page, historyOffset, updateBaseline)` and maps `DynamicList.List` through `DynamicGrpcMapper.MapToHomeItems`. It uses the response `HasMore` value for `CanLoadMore`, and saves the history offset, update baseline, and page number only after the RPC and item mapping succeed. A failed request leaves the prior page and cursors intact, disables automatic pagination, and keeps the existing user-facing error handling. Explicit refresh clears items and cursor state and requests page 1. Diagnostics identify `Dynamic/DynVideo`, page, cursor presence, source and mapped counts, and `HasMore`; they omit cursor contents and response bodies. The legacy 404 web endpoint is no longer used by this home video feed. UGC-season card type 4310 stays type 4310 and uses the target's video card fields/template; the click route opens its `Avid` in VideoDetailPage, matching the pinned sibling, instead of treating an archive ID as a PGC season ID.

The integration has not been built or exercised; runtime behavior remains unconfirmed.
