## 3. [#14 — 无法回复评论](https://github.com/ywmoyue/biliuwp-lite/issues/14)

- **Created:** 2023-02-08 01:44:50 UTC · **State:** closed
- **Reported symptom:** users could not reply to comments. In the thread, the maintainer identified it as an authentication issue and later said it was fixed.
- **Why this is a bug report:** replying is an existing action that failed, and the maintainer's diagnosis confirms a defect rather than a feature request.
- **Target evidence:** [CommentApi.cs](../../../src/BiliLite.UWP/Api/CommentApi.cs) builds `ReplyComment` with CSRF but does not set `need_cookie`. [ApiModel](../../../src/BiliLite.UWP/Api/ApiHelper.cs) defaults that flag to false. [Utils.Request](../../../src/BiliLite.UWP/Helpers/Utils.cs) ignores `need_cookie` in the POST branch and calls [HttpHelper.Post](../../../src/BiliLite.UWP/Helpers/HttpHelper.cs) with only URL, body, and supplied headers. `HttpHelper.Post` constructs a default `Windows.Web.Http.HttpClient` with no explicit Cookie header, custom filter, or app-level cookie middleware. Target login code does set cookies through `HttpBaseProtocolFilter.CookieManager`, but source inspection alone does not establish whether that default client automatically sends those app-managed cookies. In the pinned sibling, `ApiModelExtensions.Request` checks `need_cookie` on POST and calls `PostHttpResultsWithCookie`; that helper loads persisted `CookieService.Cookies` (refreshing them if empty), adds extras, and passes them to the request builder, whose `BiliRequest` calls Flurl `WithCookies`. The sibling's `ReplyComment` sets `need_cookie = true` and obtains CSRF from that cookie service.
- **Target applicability:** **unproven; do not count as a concrete defect on source evidence alone** (low confidence). There is no explicit app-level cookie injection on this POST path, but the default WinRT client may supply cookies through its protocol filter. That behavior was not validated, and the sibling's explicit cookie path cannot prove the target default client omits them.
- **Minimal possible fix idea / next action:** verify default-client cookie behavior or obtain a target reproduction showing that authenticated reply POSTs omit the required cookie; if confirmed, route this call through an authenticated POST helper. No fix is justified from this source-only assessment.
